# 商品购买与订单查询

详情页购买区展示支付宝、数量、合计和四位验证码。验证码通过后，「立即购买」在当前页面打开弹窗。用户在「信息确认」填写联系方式和查询密码，再进入「确认付款」。服务端确认到账后进入「连接账号」。正式环境启用兑换时，用户授权发送 Session、核对账号后，可提交充值并在弹窗或订单页查询结果。旧的 `/checkout/:productId` 链接仍可使用购买表单。

2026-11-10 已发布：优惠券验证生效后，购买弹窗右上角左右排列两种金额：左侧以红色大字显示优惠后的应付价格，右侧以灰色划线显示优惠前价格。修改、清空或验证失败时清除优惠展示。创建订单后使用订单快照中的实际金额及优惠前价格，重新打开进度仍显示两种价格；普通原价及免付开通订单不显示优惠划线价。

2026-11-10 已发布：账号验证错误按具体原因展示。区分 Session JSON 不完整、缺少登录令牌/邮箱/有效期、Session 已过期、充值服务拒绝、账号确认或预检会话过期、请求超时、限流及连接/响应异常。读取充值服务文档约定的 `error` / `code` 与 `detail` / `message`；仅明确的 Session 过期证据显示失效提示，网络或未知错误不推断为过期。业务说明经过凭证过滤后显示，原始 Session 和卡密不会进入错误提示。账号确认会话失效时，下一次验证会重新创建会话；验证失败保留输入，包括 HTTP 409，供用户修改后重试。「可以开通」标签仅在明确确认通过时展示。

- 联系方式支持邮箱、手机号、QQ 或微信，5–254 个字符；订单查询时去除首尾空格并忽略大小写。
- 新订单必须设置 6–14 位查询密码。密码只用于本站订单查询，不是支付宝或第三方账号密码。
- 查询密码通过随机盐 scrypt 保存；不进入订单快照、API 返回、浏览器存储或支付宝表单。
- `/api/orders` 创建订单必须包含 `productId`、`contact`、`queryPassword`、`expectedPriceCents` 和 `Idempotency-Key`。并发重试只创建一笔订单，更改密码复用同一提交编号会被拒绝。
- `/api/orders/lookup` 以 POST JSON 接收联系方式和查询密码，只查最近 50 条中密码匹配的订单。请求校验同源，限制全局 40 次/分钟、每个联系方式 8 次/分钟；错误联系方式和密码统一报错。
- 找回只向当前浏览器授予匹配订单的 8 小时访问权限，不修改原始订单归属，不能访问同一联系方式下使用其他密码的订单。过期后可重新验证。
- 原有订单未设置查询密码时仍由原浏览器凭证保护，不设置默认密码或自动开放访问。邮件验证码找回、自动交付及在线退款仍未开通。
- 支付是否可用由服务器当前配置决定。未开通时立即购买按钮不可用，不创建模拟正式订单。

数据库 schema 6 添加联系方式、密码哈希及订单访问授权表，保留历史订单、管理员账号和商品点击记录。发布前须备份，并在备份副本上验证迁移；schema 5 及更早代码不能直接运行已升级数据库。

LoveCodex 兑换由各环境服务端的 `LOVECODEX_ENABLED=true` 开启，仅处理当前环境的已付款订单。卡密按环境和商品分配，并优先使用标记优先的库存。沙箱支付不会实际扣款，但兑换仍调用 LoveCodex，请使用专用测试账号和测试卡密。Session 原文仅用于当次服务端请求，商城数据库保存兑换会话、订单查询凭证和结果。提交结果不明时只查询原单，由客服核对长期未确认的订单。

2026-11-10 仅本地修改，尚未发布：超级管理员免付开通在「验证账号并继续」时只识别 Session 中的账号邮箱，不分配卡密，也不调用绑定卡密的上游准备或验证接口；页面显示「账号信息已识别」，不提前宣称「可以开通」。点击「确认并提交充值」后，重新核对账号、Session 指纹及条款版本，再按当时的商品、环境和优先级分配库存，向上游验证并提交充值。普通付费订单流程不变，历史已分配卡密不会自动释放。

schema 21 新增 `staff_redemption_previews`，只保存账号、确认编号、Session 的 SHA-256 指纹、条款版本、最长 15 分钟的确认有效期及并发处理租约，不保存 Session 原文或登录令牌。原文仅暂留当前页面内存，确认时重新发送；关闭或刷新页面后须重新填写并识别账号，预览未确认不会占用库存。提交后的网络异常仍按原单查询，禁止重复充值。部署前须备份数据库；旧版本不能直接读取 schema 21。

购买弹窗和订单页的「开通结果」在状态下方、兑换单号上方显示「开通邮箱」。邮箱来自该订单保存的充值账号，刷新页面后仍可查看；未保存邮箱的历史订单显示「未记录」。该信息通过原有订单归属校验后的兑换状态接口返回。

「我的订单」列表在订阅成功的订单信息下显示「充值邮箱」。成功判定沿用开通结果的「充值成功」规则（结算 `PAID` 或续费 `paid`），仅付款、账号验证或充值排队不算订阅成功。邮箱读取该订单保存的实际充值账号，历史成功记录缺少邮箱时显示「未记录」。列表接口沿用订单归属及找回授权校验，不返回卡密或兑换凭证。

2026-11-10 新增列表「充值状态」，独立于「已付款 / 免付开通」展示。状态读取数据库保存的充值提交、处理、结算和续费结果，文案与详情页共用判定；`FULFILLED` 但尚未结算显示「办理完成，等待结算确认」，不提前显示成功。未付款显示「未开始」，已付款未提交显示「待充值」，结果未知继续等待确认，取消后显示「已停止」。手动刷新订单可读取最新保存状态，不通过列表发起充值或调用上游查询。此项及状态数量徽标已于 2026-11-10 发布；状态数量为 0 时隐藏徽标，保留筛选标签。

## 支付后开通超时与退款审核（2026-11-09 已发布）

新规则启用后确认付款的普通订单，按第一次付款确认时间加 30 分钟设置不可延期的开通期限。重复支付通知不会重置期限。已付款的历史订单不会在升级时批量补录期限，免付开通订单不走超时退款。2026-11-09 已发布后台审核规则，替代 2026-11-08 版本的自动退款规则。

API 进程启动后每 15 秒检查一次，无需用户保持页面打开。到期后阻止新的账号验证/充值提交，并核实是否已经开通：

- 未占用卡密：取消订单并生成待审核退款记录，暂不退款。
- 尚未提交充值但已占用卡密：查询上游，确认卡密 `AVAILABLE`、没有正在充值的订单后，取消订单并提交退款审核。
- 已提交充值：必须能够核对本次提交实际返回的上游订单号，且上游确认 `NO_CHARGE`、卡密 `AVAILABLE` 才进入退款审核。
- 已开通、已确认充值结算、已完成提前续费设置：保留订单和卡密，不触发超时退款。
- 上游仍在处理、无法确定结果、仅返回 `CANCELED` 但未确认未扣款、卡密仍占用、提交超时且未取得可靠订单号：保留订单和卡密，标记待核实；后台继续查询，不推断为失败。当前上游文档没有撤销在途充值的接口，无法安全强制取消这类订单。

确认可取消后业务订单即显示「订单已取消」，提示「退款待后台审核；款项尚未退回」。具有 `orders.refund` 权限的管理员在独立的「退款审核」菜单中确认同意或填写原因驳回；审核人、时间和备注持久保存。待审核和已驳回的记录不会发起退款或释放卡密；查看订单的权限不能审核。重复审核不会覆盖原记录或重复退款。

审核通过后重新核实上游，若已开通则保留已付款订单并停止退款。可安全退款时，原路退款复用同一个持久化退款请求号；超时或网络失败后只查询原退款单，不重复发起退款。已有部分成功退款时只退剩余款项；其他退款尚未确认时等待其结果。支付宝确认累计全额退款后，解除对应 `order_redemptions` 占用，卡密按原商品、环境、优先级自动回到「卡密管理」。回库前不删除卡密本身。

「我的订单」、订单详情及后台订单管理均展示取消状态，后台支持按「订单已取消」筛选；等待核实/退款中的订单显示具体提示。支付账本仍保留已付款事实及交易号，退款保存在独立退款账本，营业额统计继续按付款/退款时间核算，返利全额退款失效及提现余额规则继续生效。

SQLite schema 16 新增 `order_fulfillment_deadlines`、`order_cancellations`，并增加 `order_redemptions.submitted_order_no`，仅保存本次提交实际返回的上游订单号。取消记录保留退款单号、回收卡密 ID、处理状态及时间，不暴露完整卡密或上游凭证。部署前需备份数据库；跨 schema 回退前先保全新增业务数据。

schema 18 新增 `order_refund_reviews`。升级前已创建原退款单、且处于 `refund_pending` 的超时记录只继续核对原单，标记为 `system:migration`，不伪造管理员审批；尚未发起退款的记录回到核实和待审核流程。已完成退款不回滚，不为历史已付款单补建超时期限。新版本审核数据需随数据库备份保留，旧版程序无法直接读取 schema 18。

schema 19 为取消记录新增 `source`，区分超时、用户取消未付款订单与用户取消已付款订单。历史记录保留为 `timeout`；升级不新建历史订单的退款调度。

## 用户主动取消订单（2026-11-09 已发布）

「我的订单」列表和真实订单详情页均按服务端返回的 `cancelAction` 展示「取消订单」，操作前二次确认订单号、商品和金额。

- 未付款订单：先向支付宝查询；确认未付款后关闭交易并保存取消记录。查询或关单结果不明时保留原状态。查询发现已付款或之后收到有效到账通知时，保留已付款事实，不按未付款取消退款。
- 已付款订单：仅尚未提交充值、未开通、没有正在进行的账号验证或既有退款时允许申请。服务端再次核实上游，确认安全后取消并进入后台退款审核，不立即退款或释放卡密；结果不明确时等待核实。
- 已提交充值、处理中、已开通、免付开通、已关闭、已取消的订单不提供取消入口。其余订单在支付关闭或收款配置变更、无法核实交易时显示禁用的「取消订单」按钮及原因，不能提交取消。订单找回后的访问授权沿用原有归属检查。
- 详情页账号验证和充值提交期间禁用取消按钮，提交充值后立即隐藏取消入口；过期页面发起取消时服务端仍重新检查条件。重复取消不会重复关单、创建审核或退款。

取消操作使用同源 POST `/api/orders/:id/cancel`，提交 `expectedAction`，避免未付款确认弹窗意外变成已付款退款申请。列表与详情在取消后显示最新状态及退款审核提示，刷新页面仍保留。

2026-11-10 已发布：订单列表的充值状态使用分色标签（成功绿、进行中蓝、待核实橙、失败红、未开始/停止灰）；退款审核驳回说明以红色加粗显示。详情页底部「联系支持」「返回我的订单」改为统一图标的圆角描边按钮，上方分隔线，窄容器自动分行。
